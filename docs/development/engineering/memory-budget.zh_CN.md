# 内存与资源预算规则

修改缓冲区、队列、任务栈、缓存、字体、图片解码、网络协议、音频、无线资源生命周期、
依赖或分区时，必须遵循本规则。适用平台为 ESP32-C3、8 MB Flash、无 PSRAM。
本文件规定评审与验收要求；文档本身不会在固件中自动执行任务调度或分配限额。

## 每个应用只有一份当前预算

每个应用在 `docs/assets/` 维护一份当前资源预算，由其设计或交底文档链接。
资源相关代码修改必须同步更新预算。通用规则写在本文件，应用的具体大小和并发决策
写在应用预算中。基线 demo 与派生应用无需使用相同的分配额度或分区。

预算必须包含：

| 项目 | 必需信息 |
| --- | --- |
| 版本身份 | 源码检查点、镜像／ELF 身份、有效配置和分区布局 |
| 分配台账 | 所有者、最大字节数／数量、内存能力或 Flash 分区、生命周期、释放点、允许重叠的资源 |
| 执行阶段 | 各阶段存活资源、允许的后台工作和切换清理 |
| 余量 | 各受限堆／内存池的数值预留、下一次最大分配及预留理由 |
| 证据 | 实测负载、采样方法、最低值、栈余量、回收情况和未验证场景 |

条目必须标为**配置值、估算值、实测值或未验证**。分配估算不等于实测峰值；
短请求成功不能证明最大支持负载可用。

## 正确区分各类内存

- 分开统计链接时的 `.data`、`.bss` 与 IRAM、运行时系统堆、DMA 堆、LVGL 自有池、
  任务栈和 Flash。统一使用字节或 KiB。
- 芯片标称 SRAM、链接器显示的区域剩余量都不能直接当作运行时可用堆。
  不同内存能力和连续块大小会限制分配。
- 内部可逐字节访问堆使用 `MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT` 测量；
  DMA 使用驱动实际要求的能力组合。DMA 与内部堆有重叠，不能相加。
  静态池和从堆分配的任务栈也不能重复计入总量。
- 静态 LVGL 池即使内部空闲，仍占用 RAM；池内碎片和分配失败需要单独测量。
- 字体／图片位置以 ELF／MAP 和映射地址为准。Flash 常量占 Flash；解码、字形缓存
  和动态加载可能占 RAM。大字库不必然是大 RAM 占用。
- 应用 Flash 和缓存／存储 Flash 分开预留，遵循[固件布局](firmware-layout.zh_CN.md)。
  分区间搬移素材不会增加总容量；新增缓存分区不得成为基线强制要求。

## 资源归属与并发

1. 每个缓冲区、队列项、音频设备、临时分区和任务必须有明确所有者。
   定义所有权转移，以及成功、失败、超时、取消、退页和停机时的清理方式。
2. 高开销阶段默认串行；并行必须有独立的实测预算。资源预约必须覆盖请求构造、
   临时副本、网络／客户端建立、解析和清理。在大 JSON 树或目录副本分配完以后
   才取得 HTTP 锁，不能约束峰值。
3. 麦克风采集与扬声器播放必须由统一的音频所有者协调。停止 I/O 后再释放
   codec／I2S／DMA。TLS 握手前不得提前初始化闲置音频，除非该重叠已通过验收。
4. 使用缓存朗读时，先完成并验证全部临时音频，关闭网络并释放解析／请求缓冲，
   再启动 PCM。网络流式播放必须单独验收其重叠预算。
5. 后台同步、目录刷新、扫描和配网的准备或执行与当前阶段冲突时，必须延后。
   延后不得丢失待上传用户记录，资源恢复后应重试。无线窗口必须有界；关闭时释放
   相关任务、定时器和处理器。
6. 共用回复存储必须携带操作身份、模式和有效性。切换模式或取消后清空或拒绝旧结果。
   复用存储不得让故事显示问答内容，也不得改变已记录统计。
7. 按键／UI 回调不得阻塞，遵守 LVGL 锁规则。等待网络或 PCM 时不得持有 UI 锁；
   新增资源锁时必须定义锁顺序和有界的取消等待。

## 分配与负载上限

- 为输入、响应正文、JSON 节点／记录、队列深度、音频时长和缓存大小设置有限上限。
  计入终止符、对齐、分配器开销、编码膨胀及 `realloc` 新旧缓冲同时存活的情况。
- 协议允许时优先采用有界分块和所有权转移。指针队列只有生命周期安全时才节省复制。
  不得把大负载放在任务栈上，也不得永久扩大缓冲来掩盖峰值生命周期问题。
- 检查所有内存分配及任务／队列创建结果。部分初始化失败必须完整回退，不泄漏、
  不发布无效数据；清理完成后才重试。
- 任务栈根据已验收的最深调用负载与高水位证据设置，并明确预留。记录锁定 ESP-IDF
  版本的 API 单位；不得依据空闲读数统一削减任务栈。
- TLS 接收尺寸必须支持服务商实际发送的记录。修改 TLS 缓冲必须有协议和分配证据。
  不得通过关闭证书验证、看门狗或栈保护获得余量。

## 余量与诊断

为每种受限内存能力／池计算阶段边界之后还可能出现的最大分配，包含允许的并发工作。
进入该阶段必须满足：

```text
free_before >= remaining_peak_allocations + reserve
largest_before >= largest_next_allocation + fragmentation_margin
```

应用预算必须给出数值预留，并根据驱动／UI 活动、负载上限和压力证据解释理由。
预留是工程目标，不是芯片保证。未知峰值或内存能力不得标为 PASS。
堆会继续变化，因此后续大分配前需要重新检查；同时用阶段仲裁避免竞争分配。

高开销阶段前、中、后记录可用字节、适用能力的最大连续块和最低可用量，
同时记录 DMA、LVGL 池及相关任务栈余量。指标必须带固件身份及阶段／操作身份。
`heap_caps_get_minimum_free_size()` 汇总各独立堆的历史最低值，并非所有堆同时采样的
最低值；最大块的阶段采样也不是连续生命周期最低值。证据中必须说明这些限制。
参见 [ESP-IDF 堆诊断](https://docs.espressif.com/projects/esp-idf/en/release-v5.5/esp32c3/api-reference/system/heap_debug.html)。

分配失败诊断应保留申请字节数、内存能力和阶段。Hook 不得分配、阻塞或触发递归日志。
跟踪与内存破坏检查用于有界诊断，并计入其自身开销。日常日志不得暴露密钥、
私人录音或回复正文。

## 修改验收

新增或扩大资源前，先更新台账和阶段预算。不能证明预留达标时，先回收内存或串行化。
删减功能必须是明确的产品决策；优化过程中必须保持记录完整、统计一致和模式归属正确。

资源相关固件修改必须：

1. 对边界、分配／部分初始化失败、取消、所有权转移和清理运行针对性测试，
   再运行[完整门禁](build-and-test.zh_CN.md)。
2. 在已识别设备上测量匹配固件的最大支持负载。覆盖连续阶段／模式切换、
   长回复／满列表、重连、重试，以及适用时的配网开关。
3. 预热并完成清理后比较相同空闲状态。不得出现持续下降的内存趋势、分配失败、
   栈／池耗尽，且必须满足文档预留和最大块要求。声明循环次数及有界保留缓存；
   无法解释的损失判为失败。
4. 分开验证用户可见正确性、实际声音／显示效果。保留 NVS／数据并遵循已授权烧录
   规则；分别交付 Build、Host tests、Device tests 和 Unverified。

既有缺口必须在应用预算中持续可见。完整达标前可以先做减少缺口的有界修复，
但需记录修复前后证据和剩余差距。缺口未消除时不得宣称容量充足或增加无关功能。
静态检查验证文档结构，固件检查验证镜像能否装入分区；两者目前都不执行运行时
预留检查，也不能证明内存稳定。
